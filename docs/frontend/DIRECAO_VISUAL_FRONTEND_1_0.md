**Versão:** 1.0

**Status:** DIREÇÃO APROVADA PARA PROTOTIPAÇÃO  
**Escopo:** identidade visual, UX, navegação, acessibilidade, fotografia, mapa, dados, acervo, áudio e comportamento responsivo.  
**Não é:** autorização para alterar infraestrutura, banco, R2, DNS, Vercel, migrations ou conteúdo documental.

## 0. Síntese executiva

O frontend do Observatório deve materializar o conceito de **CARTOGRAFIA VIVA**: uma plataforma pública de divulgação do Observatório, do estudo e do PodObservar que se comporta como uma ferramenta tecnológica e cartográfica de alta precisão, mas cuja matéria-prima são território, pessoas, memória, pesquisa e cultura viva.

A interface deve comunicar simultaneamente:

- território;
- pesquisa;
- tecnologia;
- descoberta;
- emoção;
- sofisticação;
- curiosidade;
- cultura viva.

O projeto **não pode** parecer:

- startup;
- site governamental antigo;
- ONG genérica;
- portal de notícias;
- template corporativo;
- portfólio cinematográfico de agência;
- trabalho escolar de colagem;
- interface “hacker” cenográfica;
- dashboard frio que apaga as pessoas.

A frase-guia da direção é:

> **Uma interface cartográfica e tecnológica de ponta para divulgar pesquisa, atravessada por pessoas, vozes, fotografias e cultura viva.**

Os três pilares que precisam atingir nível excepcional são:

1. **Home — O Manifesto**
2. **Mapa / Território — A Espinha Dorsal**
3. **Acervo — O Repositório de Conhecimento**

# 1. Princípios inegociáveis

## 1.1 Tecnologia sem corporativismo

A sensação de tecnologia virá de precisão de layout, resposta rápida, microinterações, tipografia de metadados, organização dos dados, comportamento do mapa e qualidade de software.

Ela **não** virá de:

- glow excessivo;
- gradientes SaaS;
- cards genéricos;
- glassmorphism;
- ícones de startup;
- slogans comerciais;
- “AI look”.

## 1.2 Cultura viva, não folclore decorativo

Elementos territoriais como igreja, carcará, cacto, estrada, serra, linhas cartográficas e telescópio só entram quando possuem função editorial, cartográfica ou semântica.

Nenhum elemento será usado apenas porque “parece Nordeste”.

## 1.3 Pessoas no centro

Dados explicam o território; pessoas dão sentido a ele.

Fotografias, vozes, nomes, entrevistas e testemunhos devem funcionar como **evidência documental humana**, não como decoração emocional.

## 1.4 Movimento com propósito

Movimento deve responder à ação do usuário ou orientar leitura.

Não usar movimento para demonstrar habilidade técnica.

## 1.5 Acessibilidade é estrutural

A Central de Acessibilidade é uma camada de preferência e descoberta de recursos, não um “conserto” aplicado por cima de um site inacessível.

## 1.6 Dados nunca serão cenográficos

Não inventar:

- coordenadas;
- indicadores;
- IDs;
- datas;
- instituições;
- relações territoriais;
- nomes de pessoas;
- fontes;
- estados documentais.

Qualquer metadado visual deve nascer de dado verdadeiro.

# 2. Conceito visual: CARTOGRAFIA VIVA

A identidade deve fundir três camadas.

## 2.1 Camada de interface

Características:

- grade rigorosa;
- linhas finas;
- metadados em mono;
- numeração de seções;
- estados de foco/hover precisos;
- comportamento de software responsivo;
- bordas discretas;
- orientação cartográfica;
- alta legibilidade.

Sensação: **instrumento de pesquisa contemporâneo**.

## 2.2 Camada editorial

Características:

- fotografia documental;
- textos com respiro;
- voz humana;
- contexto metodológico;
- depoimentos;
- narrativa de campo;
- legendas com peso de arquivo.

Sensação: **dossiê jornalístico e documental**.

## 2.3 Camada territorial

Características:

- mata;
- serra;
- água;
- caminhos;
- topografia;
- arquitetura local;
- cultura popular;
- paisagem real.

Tudo deve ser sugerido com sutileza.

Evitar:

- papel rasgado;
- borda queimada;
- carimbo cenográfico;
- scrapbook;
- vintage falso;
- textura pesada.

# 3. Referências e o que extrair de cada uma

## 3.1 Instagram do Observatório

**É a referência de identidade mais importante.**

Extrair:

- verde-azulado institucional;
- relação visual com mata e território;
- fotografia documental;
- títulos fortes;
- presença institucional das marcas;
- linguagem gráfica conectada a pesquisa de campo;
- linhas orgânicas/cartográficas da identidade.

Não copiar literalmente o grid de posts para o site.

## 3.2 Observatório Itaú Cultural

Extrair:

- destaque visível para acessibilidade;
- tratamento institucional sem esconder conteúdo;
- acesso direto a recursos de leitura;
- clareza de navegação.

Não copiar o widget visualmente.

## 3.3 Painel de Dados / i-nove

Extrair:

- gráficos menos corporativos;
- visualização de dados com personalidade;
- composição editorial de indicadores;
- uso de ilustração como linguagem de apoio.

No Observatório, substituir metáforas genéricas por elementos territoriais verdadeiros.

## 3.4 Linear / Next.js / Supabase

Extrair somente princípios de engenharia de interface:

- rapidez;
- precisão;
- microinterações;
- estados claros;
- navegação fluida;
- densidade controlada;
- sensação de software confiável.

**Não adotar a aparência visual de SaaS.**

## 3.5 The Pudding

Extrair:

- união entre narrativa editorial e dados;
- scrollytelling apenas onde informação exige;
- mapas/gráficos como parte da narrativa;
- leitura que continua fluida apesar de elementos interativos.

# 4. Identidade institucional e marcas

## 4.1 Observatório

A marca do Observatório é a identidade principal do produto.

Usar o símbolo/wordmark oficial quando for necessário reproduzir exatamente o lettering da marca.

**Não tentar adivinhar a fonte da marca a partir do vetor.**

## 4.2 Coletivo Cultural “Tobias, sou Eu!”

A presença do coletivo deve ser **mais forte que em uma assinatura discreta de rodapé**, porque o coletivo idealiza e realiza o Observatório.

Direção aprovada:

- Hero: linha de autoria visível — `Uma iniciativa “Tobias, sou Eu!”`;
- Header/brand rail: micro-identificação do coletivo junto à marca do Observatório;
- seção institucional própria explicando idealização e realização;
- footer: presença institucional completa;
- página Sobre/Observatório: autoria do coletivo em primeiro plano.

Evitar transformar a navegação em co-branding pesado.

## 4.3 Marcas de fomento e realização

Devem aparecer em área institucional própria, respeitando a composição vigente e o manual aplicável.

O frontend não deve reorganizar régua de marcas por gosto visual sem documentação institucional.

# 5. Sistema cromático

## 5.1 Cor dominante

**Mata** é a temperatura dominante.

O verde-azulado do primeiro post e da marca do Observatório é a assinatura institucional principal.

### Regra

O valor hexadecimal definitivo deve ser extraído do arquivo oficial da identidade visual. Não “olhar e estimar” a cor.

## 5.2 Superfícies

Direção principal:

- experiência predominantemente clara;
- pedra/off-white como superfície editorial;
- mata/verde-azulado como âncoras;
- escuros para fotografia, mapa e blocos técnicos;
- milho como acento controlado;
- barro como acento territorial secundário;
- anil como apoio de dados/comparação quando fizer sentido no sistema existente.

## 5.3 Temperaturas por seção

Permitido variar predominância sem criar identidades diferentes.

Exemplo:

- Território → mata / verde-azulado;
- Pesquisa → pedra + mata;
- Dados → pedra + anil/verde-azulado;
- Pessoas → fotografia + tons naturais;
- Acervo → pedra / grafite / verde institucional;
- Prestação de Contas → neutro técnico.

## 5.4 Dark mode

O dark mode é primeira classe.

### Primeira visita

Seguir automaticamente `prefers-color-scheme` do sistema.

### Depois

Permitir override manual e persistir a escolha localmente.

O modo escuro não será apenas inversão preto/branco; deve possuir equivalentes próprios de pedra, mata, verde institucional, milho e texto secundário.

# 7. Fotografia

## 7.1 Papel da fotografia

Fotografia é protagonista documental.

Ela deve provar presença no território, não apenas embelezar a interface.

## 7.2 Hero oficial

**Imagem oficial definida para o Hero 1.0: `home.jpg`.**

Motivos:

- conduz o olhar para dentro do território;
- mostra trabalho de campo;
- registra linguagem local;
- possui profundidade;
- funciona como convite à descoberta.

## 7.3 Tratamento permitido

Permitido:

- crop;
- contraste;
- exposição;
- overlay escuro;
- adaptação para light/dark;
- art direction por breakpoint.

Evitar:

- filtro vintage;
- ruído pesado;
- cor artificial;
- efeito “cinematográfico” que descaracterize o registro;
- substituição por imagem gerada.

## 7.4 Art direction

Desktop e mobile podem usar crops diferentes da mesma fotografia.

Desktop: preservar pessoas + placas + profundidade horizontal.

Mobile: aproveitar melhor a verticalidade do arquivo original.

## 7.5 Fotografia em mapas/drawers

Por padrão, manter cor documental.

Preto e branco só quando houver justificativa editorial clara, nunca como estilo universal.

## 7.6 Metadados de fotografia

Quando disponíveis e publicáveis:

- local;
- data;
- contexto;
- autoria/crédito;
- relação com pesquisa.

Não inventar ficha de acervo.

# 10. Mapa / Território — assinatura do produto

## 10.1 Estado inicial aprovado

O mapa abre mostrando **Sergipe inteiro inclinado**, com efeito de espessura/pseudo-3D semelhante à referência enviada.

A intenção não é imitar Google Earth.

A sensação desejada vem de:

- ângulo;
- sombra;
- espessura;
- separação dos municípios;
- hierarquia de camadas.

## 10.2 Leitura territorial

O mapa deve diferenciar claramente:

- municípios do Vale do Rio Real;
- foco da pesquisa;
- Tobias Barreto;
- municípios relacionados ao projeto;
- São Cristóvão em papel distinto de pesquisa/comparação, não como município do Vale;
- pontos/equipamentos quando houver coordenadas confirmadas.

## 10.3 Macro → Micro

### Macro / Pôster

Sergipe inteiro, inclinado, imponente, quase cartaz cartográfico.

### Micro / Ferramenta

Ao interagir:

- zoom;
- pan;
- pitch controlado;
- seleção;
- coordenadas verdadeiras;
- limites municipais;
- pontos;
- drawer de dados.

## 10.4 Arquitetura técnica proposta

**Proposta para validação técnica, não implementação automática:**

- SVG server-side atual como fallback/pôster/acessibilidade;
- MapLibre GL JS como ilha client-side para interação avançada.

Essa proposta **altera a decisão arquitetural atual de mapa exclusivamente server-side SVG** e, portanto, antes de implementação deve gerar uma nova decisão arquitetural/ADR que explicite a evolução e seus motivos.

Não substituir silenciosamente a arquitetura existente.

## 10.5 Coordenadas

Estrutura mínima para um ponto exato:

```text
ID
Nome
Tipo
Latitude
Longitude
Fonte da coordenada
Data da verificação
Estado de publicação
```

Sem coordenada confirmada, não há pin exato.

## 10.6 Drawer

Desktop: painel lateral.

Mobile: bottom sheet amplo.

Conteúdo típico:

- ID/metadado;
- nome do local;
- tipo;
- coordenadas verdadeiras;
- fotografia;
- texto editorial;
- dados;
- links para pesquisa/acervo.

## 10.7 Pins e thumbnails

Não converter todos os pins em fotografias.

Miniatura fotográfica apenas para:

- item selecionado;
- história em destaque;
- contexto em que a fotografia aumenta compreensão.

# 12. Movimento

## 12.1 Intensidade

Site geral: **3–4/10**.

Mapa: **10/10 em capacidade de interação**, não em animação autônoma.

## 12.2 Timing orientativo

- hover: 120–180ms;
- reveal: 200–300ms;
- drawer: 200–280ms;
- transições de página: instantâneas/curtas;
- sem loader teatral;
- sem scroll sequestrado.

## 12.3 Scroll reveal

Permitido apenas se:

- conteúdo já ocupa seu espaço;
- animação não bloqueia leitura;
- respeita reduced motion;
- não causa reflow agressivo.

## 12.4 Parallax

Evitar por padrão.

## 12.5 Cursor

Cursor customizado: **não usar**.

## 12.6 Mapa

Pan/zoom/seleção devem parecer fluidos.

Pins podem pulsar de forma muito leve somente quando houver valor de descoberta e com `prefers-reduced-motion` respeitado.

# 13. Navegação

## 13.1 Desktop

Header hide-on-scroll.

Marca pequena e precisa.

Menu horizontal.

Acessibilidade e Prestação de Contas isoladas e visualmente importantes.

## 13.2 Prestação de Contas

Deve permanecer fácil de localizar.

Não esconder dentro de submenu.

É um eixo de transparência do projeto.

## 13.3 Mobile

Prioridades:

1. velocidade;
2. navegação;
3. legibilidade.

A composição mobile não precisa copiar desktop.

A solução final de navegação mobile deve ser prototipada, com preferência por padrões de uso com uma mão e alvos grandes.

Evitar hambúrguer genérico se uma solução mais clara for validada, mas não sacrificar reconhecimento/usabilidade apenas por originalidade.

# 14. Acessibilidade

## 14.1 Princípio

O site deve funcionar corretamente antes de qualquer configuração na Central de Acessibilidade.

## 14.2 Central de Acessibilidade

Direção funcional:

```text
ACESSIBILIDADE

Tema
- Claro
- Escuro
- Sistema

Texto
- A−
- A
- A+

Contraste
- Alto contraste

Movimento
- Reduzir animações

Leitura
- Ouvir esta página

Navegação
- Atalhos e teclado

Ajuda
- Conheça os recursos
- Reportar uma barreira
```

O desenho final deve ser próprio do Observatório, não cópia visual do Itaú Cultural.

## 14.3 Requisitos estruturais

- navegação completa por teclado;
- skip link;
- foco visível;
- headings corretos;
- landmarks semânticos;
- contraste adequado;
- não depender apenas de cor;
- alvos de interação confortáveis;
- reduced motion;
- imagens com alt coerente;
- tabelas semânticas;
- áudio com controles acessíveis;
- transcrições;
- alternativa textual para mapa.

## 14.4 Mapa acessível

Mapa visual e lista pesquisável devem representar o mesmo estado de dados.

Exemplo:

- selecionar Recanto da Serra na lista → mapa focaliza;
- clicar no ponto do mapa → lista/painel seleciona o mesmo registro.

Nenhuma informação essencial pode depender exclusivamente de canvas/WebGL.

- Home;
- Sobre/Observatório;
- Território;
- Pesquisa.

Controles mínimos:

- play/pause;
- progresso;
- duração;
- velocidade;

## 15.4 PodObservar

- áudio;
- transcrição;
- participantes;

# 16. Dados e indicadores

## 16.1 Princípio

Número grande pode ser usado quando representa magnitude real e relevante.

Não usar linguagem promocional.

## 16.2 Estrutura visual recomendada

Indicador principal + metadado técnico + contexto editorial.

Exemplo conceitual:

```text
[NÚMERO REAL]
LABEL DO INDICADOR

FONTE / ...
PERÍODO / ...
MÉTODO / ...
```

## 16.3 Visualizações

Preferir, quando adequadas aos dados:

- linhas;
- área;
- dispersão;
- barras limpas;
- mapas;
- tabelas;
- infográficos editoriais.

Evitar por padrão:

- pizza multicolorida;
- gráfico 3D;
- excesso de cores;
- cards KPI de SaaS.

## 16.4 Tabelas

Tabelas podem ser protagonistas.

Características:

- linhas de 1px;
- headers precisos;
- mono para metadados;
- ótima responsividade;
- sem perda de semântica;
- scroll interno quando necessário, nunca overflow da página.

# 17. Acervo

## 17.1 Metáfora

**Arquivo Público + Explorador de Documentos**.

Não parecer:

- biblioteca antiga;
- prateleira decorativa;
- museu excessivamente curado;
- grid de e-commerce.

## 17.2 Estrutura visual

Preferir linhas/listas/fichas técnicas a uma parede de cards.

Exemplo conceitual:

```text
ACERVO / 008 ITENS

[FILTROS]
TIPO / TERRITÓRIO / ANO

────────────────────────────────
A02
RELATÓRIO TÉCNICO
Recanto da Serra
PDF · ...
                         ABRIR →
────────────────────────────────
```

Somente dados reais.

## 17.3 Filtros

Possíveis eixos, desde que existam no modelo:

- tipo;
- território;
- ano;
- documento/evidência;
- status publicável quando apropriado ao público.

Não expor estados internos/restritos desnecessariamente.

- filtros;
- metadados;
- impressão;
- acessibilidade;

- não comprometer 375px.

## 21.3 Impacto visual

No mobile, impacto fotográfico e mapa não podem comprometer leitura ou performance.

# 22. Performance e sensação de software

A sensação high-tech deve vir de performance real.

Diretrizes:

- server components por padrão;
- JS client-side somente onde necessário;
- mapa como ilha interativa;
- imagens responsivas;
- lazy loading coerente;
- sem vídeo pesado no Hero por padrão;
- sem animações bloqueantes;
- sem biblioteca de motion pesada se CSS/Web Animations resolver;
- transições que respeitem reduced motion.

# 23. Elementos gráficos aprovados

## Usar

- numeração de seções: `01 — Território`;
- datas e metadados mono;
- coordenadas verdadeiras;
- cruzes de registro;
- linhas técnicas finas;
- linhas pontilhadas sutis;
- fichas de acervo;
- hover fotográfico discreto;

- cursor customizado;
- papel rasgado;
- bordas queimadas;
- carimbos cenográficos;
- glow exagerado;
- color-fading caótico;
- parallax frequente;
- loader cinematográfico;
- glassmorphism pesado;
- gráfico 3D;
- gráfico pizza multicolorido;
- card SaaS repetitivo.

# 29. Decisões fechadas nesta versão 1.0

- Conceito: **CARTOGRAFIA VIVA**.
- Hero oficial: **`home.jpg`**.
- Hero: fotografia full-bleed + overlay escuro + marca/título.
- Título: nome completo do Observatório.
- Autoria: **“Uma iniciativa ‘Tobias, sou Eu!’”**.
- Presença do coletivo: **ampliada**.
- Menu: **Observatório · Território · Pesquisa · Dados · PodObservar · Acervo**.
- Acessibilidade: utilidade isolada e estrutural.
- Prestação de Contas: utilidade isolada e permanente.
- Light/dark: ambos primeira classe.
- Primeira visita: tema segue **sistema operacional**.
- Narração humana primeira fase: **Home + Sobre/Observatório + Território + Pesquisa**.
- Mapa inicial: **Sergipe inteiro inclinado**.
- Mapa: peça central e ferramenta de consulta.
- Fotografia: documental e real.
- Movimento geral: **3–4/10**.
- Movimento/capacidade do mapa: **10/10**, sempre orientado por interação.
- Tipografia-base: **Archivo + Literata + IBM Plex Mono**.
- Acervo: **Arquivo Público + Explorador de Documentos**.
- Sala do Avaliador: rigor, não ornamentação.
- Mobile: velocidade + navegação + legibilidade.
- Home, Território e Acervo são os três focos excepcionais.
